# 知的障害者法©️ v0.6

## 発明種別

**🤝 協働方法©️**

AIが原典の解析、価値候補・機能候補・実装先候補の比較、変換、実測整理、原因診断を担当し、人間側が原典の意味確認、実演・実機操作、公開、現実反応の確認を担当する。

## 一行定義

**一つの原典の核を保ったまま、まず相手に起こしたい価値を選び、次にその価値を実現する機能・体験へ変換し、最後に最適な実装先を選んで最小実装し、実測から原典・変換ルール・実行環境を学習更新する方法。**

## v0.6のゴール

v0.5は「どの変換先を試すか」を選べるようにした。

v0.6では、変換先をいきなり媒体名で選ばず、次の3段で決める。

```text
原典
↓
変えてはいけない核
↓
① 価値を選ぶ
↓
② 機能・体験を選ぶ
↓
③ 実装先を選ぶ
↓
最小実装
↓
実測
↓
原典 / 変換ルール / 実行環境・流通を分離診断
↓
原典・変換器・選択基準を更新
```

**重要：YouTube、Udemy、noteなどの媒体名は最初の答えではなく、最後に選ぶ実装先。**

## v0.6｜3段選択

### 1｜価値を選ぶ

相手に何を起こしたいかを先に決める。

候補例：

- 知る
- 理解する
- 学ぶ
- 使う
- 判定する
- 実行する
- 比較する
- 選ぶ
- 記録する
- 継続する

### 2｜機能・体験を選ぶ

その価値を起こすために、何の形が必要かを決める。

候補例：

- 記事
- 動画
- 音声
- 講座
- PDF
- チェックリスト
- テンプレート
- 診断
- FAQ
- 専用AI
- Webアプリ
- ワークフロー
- 自動化

### 3｜実装先を選ぶ

その機能をどこで動かすかを決める。

候補例：

- Notion
- note
- YouTube
- Podcast
- Udemy
- Web
- ChatGPT系
- SNS
- 電子書籍
- メール
- その他の実行環境

## 具体例

同じ原典でも、狙う価値によって変換先が変わる。

```text
原典：案件の地雷を見抜く方法

理解する
→ 動画
→ YouTube

学ぶ
→ 講座
→ Udemy

使う
→ チェックリスト / テンプレート
→ PDF / Notion

判定する
→ 診断機能
→ Web

実行する
→ 専用AI / Webアプリ
→ ChatGPT系 / Web
```

## v0.6で直したv0.5の弱点

1. **媒体先行をやめた**
   - YouTubeやUdemyを先に決めない。

2. **価値と媒体を分離した**
   - 「何を起こしたいか」と「どこで出すか」を別の判断にした。

3. **機能化を正式に追加した**
   - 記事・動画だけでなく、テンプレート、診断、専用AI、アプリ、ワークフローまで変換対象にした。

4. **機能と実装先を分離した**
   - 例：「診断」が機能、「Web」が実装先。

5. **媒体を最後の選択へ下げた**
   - 価値 → 機能 → 実装先の順にすることで、媒体ありきの変換を防ぐ。

## 入力

- 原典知的資産
- 変えてはいけない核
- 想定する相手
- 起こしたい価値・変化
- 機能・体験候補
- 実装先候補
- 需要信号
- 制作コスト
- 原典適合度
- 実装可能性
- 公開前に決める成功指標
- 過去の変換実績
- 公開後の実測値

## 出力

- 選択した「価値 → 機能・体験 → 実装先」の3段構造
- 各選択理由
- 最小成果物または最小機能
- 事前成功指標
- 公開後の実測値
- 原典 / 変換ルール / 実行環境の原因診断
- 原典から各派生物までの系譜
- 更新された再利用可能な変換ルール

## 標準工程

1. 原典を選ぶ。
2. 変えてはいけない核を一文で固定する。
3. 誰に何を起こしたいかを決める。
4. 価値候補を並べる。
5. 最初に狙う価値を1つ選ぶ。
6. その価値に必要な機能・体験を選ぶ。
7. その機能を実現できる実装先を比較する。
8. 需要信号・制作コスト・原典適合度・実装可能性から実装先を1つ選ぶ。
9. 専用変換ルールと成功指標、撤退・修正条件を事前に決める。
10. AIで最小実装へ変換し、人間側で実例・判断・実画面・体験を加えて確認する。
11. 公開または運用して実測する。
12. 結果を「原典 / 変換ルール / 実行環境・流通」に分けて診断する。
13. 原典・機能変換ルール・実装先選択基準を更新し、当たり変換ルールを別原典にも再利用する。

## 原因診断の3層

### 1｜原典

中身の核そのものに問題があるか。

例：価値が弱い、前提が欠けている、対象者の困りごととずれている。

### 2｜変換ルール

原典は成立しているが、価値を機能へ変換する方法に問題があるか。

例：理解させたいのに説明構造が弱い、判定させたいのに質問項目が足りない、専用AIなのに判断ルールが曖昧。

### 3｜実行環境・流通

原典と機能は成立しているが、実装先や届け方に問題があるか。

例：タイトル、検索流入、サムネイル、販売導線、UI、投稿タイミング、プラットフォーム内露出。

## NG例

- 最初からYouTubeやUdemyなど媒体名だけで変換先を決める。
- 起こしたい価値を決めずに制作する。
- 記事・動画だけを変換先だと思い込む。
- 機能と実装先を混同する。
- 専用AIやアプリにしただけで価値が上がったと断定する。
- 候補を比較せず全媒体・全機能へ一斉展開する。
- 原典の核を決めずに変換する。
- 媒体ごとの成功条件を同じ数字で判定する。
- 公開後に都合の良い指標だけ選ぶ。
- 伸びない原因を即座に原典の価値不足と断定する。
- 派生物から派生物へ伝言ゲームを続ける。
- どの原典・どの変換ルールから作られたか記録しない。

## バージョン履歴

- **v0.1**：note等の既存素材をUdemy講座へ変換する発想から開始。
- **v0.2**：需要観測・最小制作・公開後実測・撤退/増幅を追加。
- **v0.3**：Udemy中心から離れ、原典 → note / Udemy / YouTube / PDF / SNS / 音声など複数媒体への変換へ拡張。
- **v0.4**：媒体だけでなく、対象者・長さ・用途・提供形態・無料/有料など実行条件そのものを変換対象へ拡張。
- **v0.5**：変換先選択、専用アダプター、成功指標の事前固定、3層原因診断、系譜管理、当たり変換ルールの再利用を追加。
- **v0.6**：変換先選択を「媒体」から「価値 → 機能・体験 → 実装先」の3段へ分解し、知識を記事・動画だけでなく診断・専用AI・アプリ・ワークフローへ機能化できる構造へ拡張。

## v0.6の位置づけ

**v0.6 = 価値から機能を設計し、その後で実装先を選ぶ。**
