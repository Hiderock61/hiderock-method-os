# 020｜知的障害者法©️ v0.6

## 発明種別

**🤝 協働方法©️**

AIが、原典解析、核抽出、到達状態の仮設計、価値タイプ分類、機能・体験候補の比較、実装先候補の比較、最小実装への変換、成功指標の事前設計、実測整理、原因診断、系譜管理を担当する。

人間側は、原典の意味確認、本人にしか分からない意図・体験・判断の補足、実機操作、公開、撮影・録音・投稿、実際の利用、現実反応の確認などを担当する。

この方法はAI単独では完結しない。**AI内部の設計と、人間側の現実実装・観測の往復で成立する。**

---

## 一行定義

**一つの原典の核を保ったまま、AIが「誰をどんな到達状態へ動かすか」を先に定め、そのための価値 → 機能・体験 → 実装先を順番に選び、最小実装して現実で測り、原典・変換ルール・実行環境・測定設計を学習更新する方法。**

# 0｜このファイルの目的

このファイルは、知的障害者法©️ v0.6の**GitHub側設計図・AI復元仕様**である。

別端末、別チャット、別のChatGPT、Claude、Geminiその他のAIが読んでも、同じ方法をできるだけ同じ順番・同じ思想で再起動できることを目的とする。

重要なのは、利用者が内部工程を暗記することではない。

> **内部は複雑でよい。入口は簡単に保つ。**

利用者側は、原則として次のような短い入力だけでも起動できる。

```text
これを知的障害者法©️で展開して。
```

原典が明確な場合：

```text
このNotionを知的障害者法©️ v0.6で進めて。
```

実装先の希望がある場合：

```text
これを知的障害者法©️で、YouTube候補として見て。
```

AIは短い入力だからといって、利用者へ内部工程を全部質問し返してはいけない。合理的に仮置きできる部分はAI側で組み、**結果を左右する本当に必要な確認だけを人間側へ返す。**

# 1｜表の操作と裏の処理を分離する

## 1-1｜利用者が覚えること

利用者が毎回覚えるべき操作は、基本的に次の1点でよい。

> **「この原典を知的障害者法©️でやって」**

必要なら追加で、YouTubeにしたい、音声にしたい、売れる形を探したい、初心者向けにしたい、何に変換できるか見たい、アプリ化できるか見たい、まず小さく試したい、などを言う。

これらは内部工程そのものではなく、**制約・希望・探索方向**として扱う。

## 1-2｜AIが内部で必ずやること

AIは短い入力を受けたら、内部で最低限次を仮組みする。

```text
原典
↓
変えてはいけない核
↓
対象者
↓
到達状態
↓
価値タイプ
↓
機能・体験候補
↓
実装先候補
↓
最初の一枝
↓
最小実装
↓
成功指標
↓
現実実測
↓
4層原因診断
↓
更新・再利用
```

利用者が「詳しく見せて」と言わない限り、この全工程を毎回そのまま長文で表示する必要はない。

# 2｜原典

## 2-1｜原典とは何か

原典は、変換の親になる知的資産である。

候補：Notionページ、note記事、会話ログ、本人の実体験、手順書、方法©️、PDF、講義メモ、音声メモ、YouTube台本、既存講座、Web記事、制作記録、複数資料を統合した正本など。

原典は「最初に公開された媒体」を意味しない。note記事が先に存在していても、その後Notionに整理された正本が親になることがある。

## 2-2｜派生物を親にしない

原則：

```text
原典 → YouTube
原典 → Podcast
原典 → Udemy
原典 → PDF
原典 → 専用AI
```

避ける：

```text
原典 → note → YouTube → Podcast → PDF
```

派生物を何度も親にすると、削除・誇張・省略・誤変換が累積し、原典の意味核が漂流するため。

---

# 3｜変えてはいけない核

核は、媒体や形式を変えても維持すべき意味・価値・判断基準である。

### 不変項候補

- 中核となる主張
- 事実関係
- 根拠
- 定義
- 判断基準
- 本人の実体験で重要な部分
- 例外条件
- 不確実性
- 禁止している誤解

### 可変項候補

- タイトル
- 冒頭フック
- 長さ
- 順番
- 語り口
- 見出し
- 画像
- 音声
- 演習
- CTA
- 価格
- UI
- 配信場所
- 対象者向けの説明量

AIは、核を守るために形式を変える。形式を守るために核を歪めてはいけない。

# 4｜到達状態を先に作る

## 4-1｜v0.6の重要ヤスリ

「価値」を単語だけで決めない。

悪い例：

```text
価値 = 判定する
```

これでは、誰が、何を、どんな場面で、どこまで判定できれば成功なのかが分からない。

AIはまず次の形式で**到達状態**を一文で仮固定する。

```text
［誰］が、［どんな場面で］、［何をできる・分かる・選べる状態］になる。
```

例：

```text
フリーランス初心者が、案件へ応募する前に、募集文から危険信号を自分で確認して応募可否を判断できるようになる。
```

## 4-2｜到達状態はAIが仮置きしてよい

利用者が毎回この一文を書く必要はない。原典と会話から合理的に推定できる場合、AIが先に仮案を作る。本人の意図とずれている場合だけ人間側が修正する。

AIは「対象者は誰ですか？」「目的は？」「価値は？」と毎回質問票のように聞いてはいけない。

---

# 5｜価値タイプ

到達状態を作った後、整理のために価値タイプを付ける。

- **知る**：存在・概念・選択肢を認識する
- **理解する**：因果・仕組み・違いを掴む
- **学ぶ**：再現可能な手順や技能を身につける
- **使う**：実作業に適用する
- **判定する**：条件から評価・分類・判断する
- **比較する**：複数候補の違いを見る
- **選ぶ**：候補から意思決定する
- **記録する**：情報を再利用可能な形で残す
- **継続する**：習慣・運用を維持する
- **実行する**：処理そのものを行う

**到達状態が主、価値タイプはタグ。**

---

# 6｜機能・体験を選ぶ

機能・体験は、その到達状態を起こすために利用者へ提供する働き方である。

候補：記事、動画、音声、講座、PDF、チェックリスト、テンプレート、FAQ、ワークシート、診断、比較表、シミュレーター、専用AI、チャットボット、Webアプリ、自動化、ワークフロー、メール連載、ワークショップなど。

## 6-1｜媒体と機能を混ぜない

```text
診断 = 機能
Web = 実装先
```

```text
講座 = 機能・体験
Udemy = 実装先
```

```text
動画 = 機能・体験
YouTube = 実装先
```

この分離によって、同じ診断をWebアプリ、専用AI、Notionテンプレなど複数の環境へ実装できる。

---

# 7｜実装先を選ぶ

実装先は、選んだ機能・体験を実際に動かす環境である。

候補：note、YouTube、Podcast配信環境、Udemy、Notion、PDF、Kindle等の電子書籍、Webサイト、Webアプリ、ChatGPT系、SNS、メール、その他の配信・販売・実行環境。

## 7-1｜実装先は原則として最後に選ぶ

```text
原典
→ 到達状態
→ 価値
→ 機能・体験
→ 実装先
```

YouTube、Udemy、note等の媒体名を先に置かない。

## 7-2｜利用者が実装先を指定した場合

利用者が「YouTubeにしたい」と明示した場合、その指定を無視しない。YouTubeは**実装先制約**として固定し、

```text
この原典をYouTube上で機能させるなら、どの到達状態・動画体験が最も自然か
```

を逆算する。

原典と実装先の相性が著しく悪い場合は、禁止せず、理由を示して代替候補を出す。

---

# 8｜変換先選択の評価軸

候補は「AIで作れるか」だけで決めない。

1. **需要信号**：その困りごと・用途・検索・購買・利用ニーズが存在するか
2. **原典適合度**：その原典が候補機能に向いているか
3. **制作コスト**：時間、撮影、編集、実装、維持費等
4. **実装可能性**：現在のツール・技能・端末・サービスで実現可能か
5. **検証速度**：短期間で反応を取れるか
6. **再利用性**：当たったルールを別原典へ移植できるか
7. **運用負荷**：公開後の更新・問い合わせ・保守が重すぎないか

AIは候補を無制限に増やすより、最初に試す一枝を絞る。

---

# 9｜最小実装

最初から完成版を作らない。最小実装とは、**仮説を現実で検証するために必要な最小サイズ**である。

例：

- YouTube：いきなり20本ではなく1本
- Udemy：巨大講座ではなく成立する最小講座構成
- 診断：フル機能アプリではなく質問5〜10個の簡易版
- 専用AI：複雑な外部連携より先に会話フローを検証
- PDF：100ページではなく10ページ前後の実用品

「小さい」は品質を低くする意味ではない。**検証に不要な範囲を作らない**という意味。

---

# 10｜成功指標は公開前に置く

公開してから都合のよい数字だけを選ばない。成功指標は到達状態から逆算する。

### 知る
表示、到達、クリック、新規閲覧。

### 理解する
視聴維持、読了、質問内容、理解確認。

### 学ぶ
完了率、演習実行、再現率。

### 使う
ダウンロード、実利用、継続利用。

### 判定する
診断完了、判断一致率、再利用。

### 実行する
タスク完了、処理成功、時間短縮、エラー率。

プラットフォーム指標と、本当に起こしたい価値を混同しない。再生数が多いことと、理解・購入・満足・再利用が高いことは別である。

---

# 11｜実測後の4層原因診断

結果を一括で成功・失敗としない。

## 11-1｜原典

中身の核そのものに問題があるか。

例：価値が弱い、前提が欠ける、対象者とズレる、根拠不足、実例不足。

## 11-2｜変換ルール

原典は成立しているが、到達状態を機能へ変換する方法に問題があるか。

例：YouTubeなのに文章読み上げ、Udemyなのに練習がない、診断なのに質問項目が弱い、専用AIなのに判断基準が曖昧。

## 11-3｜実行環境・流通

原典と機能は成立しているが、届け方・実装環境に問題があるか。

例：タイトル、サムネイル、検索導線、価格、UI、投稿タイミング、プラットフォーム内露出、販売導線。

## 11-4｜測定

そもそも評価方法が正しいか。

例：母数不足、計測期間が短すぎる、成功指標が到達状態と無関係、データ取得漏れ、予測値と実測値が混ざる。

この4層を分けることで、YouTubeで伸びなかったから原典が悪い、という短絡を防ぐ。

# 12｜AIが確認する条件 / 確認しない条件

## 12-1｜AIが仮置きしてよいもの

- 原典候補
- 対象者候補
- 到達状態の初稿
- 価値タイプ
- 機能候補
- 実装先候補
- 比較軸
- 最小実装案
- 仮の成功指標

## 12-2｜人間確認を優先するもの

- 本人にしか分からない意図
- 実体験の事実関係
- 公開してよいか
- 本人名義で断定してよいか
- 撮影・録音・実機操作が必要か
- 有料販売条件
- 本人の価値観に関わる重要判断

## 12-3｜質問を減らす原則

AIは、答えを合理的に仮置きできる質問を毎回利用者へ投げない。

悪い例：

```text
対象者は誰ですか？
目的は何ですか？
媒体は何ですか？
長さは何分ですか？
価格はいくらですか？
```

良い例：

```text
原典から見ると、まず「初心者が自分で判定できる状態」を狙うのが自然。
最小機能はチェックリスト、実装先はPDFかNotionが軽い。
ここだけ意図が違うなら直して。
```

# 15｜当たり変換ルールを資産化する

この方法で蓄積する資産は3種類ある。

1. **原典資産**：何を伝える・使う・判断するための知識か
2. **変換資産**：その知識を、特定の到達状態・機能・実装先へどう変えると機能するか
3. **観測資産**：どの条件で、どんな反応が現実に起きたか

つまり蓄積するのは：

> **知識 × コンバーター × 現実データ**

---

# 16｜標準工程 v0.6

1. 利用者の短い入力から原典を特定する。
2. 変えてはいけない核を一文で仮固定する。
3. 「［誰］が［どんな場面で］［何をできる / 分かる / 選べる状態］になる」の形式で到達状態を作る。
4. 到達状態へ価値タイプを付ける。
5. その価値に必要な機能・体験候補を比較する。
6. 最初に試す機能を1つ選ぶ。
7. その機能を実現できる実装先を比較する。
8. 需要信号・制作コスト・原典適合度・実装可能性・検証速度から実装先を1つ選ぶ。
9. 専用変換ルールと成功指標・撤退 / 修正条件を事前に決める。
10. AIで最小実装へ変換する。
11. 人間側の実例・判断・実画面・体験を必要に応じて加えて確認する。
12. 公開または運用する。
13. 実測値を記録する。
14. 原典 / 変換ルール / 実行環境・流通 / 測定の4層で診断する。
15. 原典・機能変換ルール・実装先選択基準・測定設計のどこを更新するか決める。
16. 当たり変換ルールを別原典にも再利用する。
17. 別端末・別AIでも復元できるよう系譜を残す。

# 18｜NG例

- 利用者に内部工程を毎回すべて入力させる。
- 価値を「理解する」「判定する」等の単語だけで終わらせる。
- 誰がどうなるかという到達状態を固定しない。
- 最初からYouTubeやUdemyなど媒体名だけで変換先を決める。
- 起こしたい価値を決めずに制作する。
- 記事・動画だけを変換先だと思い込む。
- 機能と実装先を混同する。
- 専用AIやアプリにしただけで価値が上がったと断定する。
- 候補を比較せず全媒体・全機能へ一斉展開する。
- 原典の核を決めずに変換する。
- 公開後に都合のよい成功指標だけ選ぶ。
- 媒体ごとの成功条件を同じ数字で判定する。
- 伸びない原因を即座に原典の価値不足と断定する。
- 母数不足や測定設計の問題を無視する。
- 派生物から派生物へ伝言ゲームを続ける。
- 実測なしで変換ルールを成功パターンとして固定する。
- どの原典・どの変換ルールから作られたか記録しない。
- 別端末・別AIで古い説明を優先し、正本より前の版へ巻き戻す。

# 19｜標準コピペ用プロンプト

```text
知的障害者法©️ v0.6で進める。
利用者に内部工程を毎回入力させない。
入力が短くても、AI側で原典→変えてはいけない核→到達状態→価値タイプ→機能・体験→実装先→最小実装→成功指標まで仮組みする。

価値は「知る / 理解する / 学ぶ / 使う / 判定する / 実行する」等の単語で終わらせず、まず「［誰］が［どんな場面で］［何をできる / 分かる / 選べる状態］になる」という到達状態を一文で固定する。

媒体名は原則として最後に選ぶ実装先として扱う。ただし利用者がYouTube等を明示指定した場合は実装先制約として尊重する。

AIが合理的に仮置きできる対象者・価値・機能・実装先候補は先に案を出し、本人の意図・実体験・公開判断など結果を左右する箇所だけ確認する。

最小実装後は、成功指標を到達状態から逆算して実測し、原典 / 変換ルール / 実行環境・流通 / 測定の4層で原因分離する。

派生物から派生物へ伝言ゲームをせず、原則として原典へ戻って各枝を作る。
内部は複雑でも入口は簡単に保ち、必要がない限り利用者へ内部工程を全部見せない。
```
